# ארכיטקטורה והחלטות טכנולוגיות

## בקצרה

```
 טלפון של לוחם/ת          טלפון/מחשב של הצוות
        │                         │
        ▼                         ▼
 ┌──────────────────────────────────────────┐
 │  אפליקציית ווב סטטית (Vite + React + TS)  │  אחסון סטטי (GitHub Pages / Cloudflare Pages)
 │  CSP קשוח · ניתוב hash · עברית/RTL        │  בלי שרת, בלי סודות
 └──────────────┬───────────────────────────┘
                │ HTTPS בלבד (JWT ב-Authorization)
 ┌──────────────▼───────────────────────────┐
 │  Supabase (EU, פרנקפורט)                 │
 │  ├─ Auth: אימייל+סיסמה, הרשמה עצמית סגורה │
 │  ├─ PostgREST: טבלאות מוגנות RLS          │
 │  ├─ פונקציות SQL: API ציבורי ו-API צוות   │  ← כל הלוגיקה העסקית והאימות
 │  ├─ Edge Function staff-admin             │  ← ניהול משתמשים (service role)
 │  └─ Postgres 17: אילוצים, טריגרים, יומן   │
 └──────────────────────────────────────────┘
```

## למה כך

| החלטה | חלופות שנבחנו | הסיבה |
|-------|---------------|-------|
| **Supabase** (Postgres + Auth + API) | שרת Node משלנו + Postgres, Firebase | Postgres אמיתי עם אילוצים ו-RLS; אימות מוכח עם הגבלת ניסיונות מובנית; גיבוי יומי בתוכנית Pro; 25$ לחודש בתוך התקציב; כבר בשימוש בסטודיו (תחזוקה מוכרת) |
| **הלוגיקה בבסיס הנתונים** (פונקציות `security definer` + RLS) | API בשרת ביניים | אין שרת שצריך לתחזק או לאבטח; כל בקשה עוברת אותה אכיפה, גם אם מישהו עוקף את הממשק; בדיקות האבטחה רצות ישירות מול ה-API |
| **Vite + React SPA** | Next.js (ייצוא סטטי) | בלי סקריפטים מוטמעים, ולכן CSP קשוח (`script-src 'self'`) על כל אחסון סטטי; Next מייצא סקריפטים inline |
| **ניתוב hash** (`/#/r/קוד`) | ניתוב רגיל | עובד בכל אחסון סטטי בלי הגדרות; הטוקן האישי (`#/m/…`) לא נשלח לשרת ולא נרשם בלוגים |
| **ממשק שליחת וואטסאפ ידני** (wa.me) | WhatsApp Business API | השאלון: אוטומציה "בהמשך"; ה-API דורש אישור Meta ועלות להודעה; כך אין שליחה בלי אדם שלוחץ |
| **QR עצמי + רשימה בטלפון** | סורק אצל מתנדב | השאלון (ש׳15–16) מעדיף צ׳ק־אין עצמי, ורשימה בטלפון כגיבוי |
| **גרפים ב-SVG/CSS שלנו** | ספריית גרפים | אין תלות נוספת, RTL נכון, עיצוב אחיד |
| **פוסט/סטורי ב-Canvas בדפדפן** | Canva API / AI | בלי עלות ובלי שליחת נתונים לצד שלישי; עובד מיד |

## שכבות בבסיס הנתונים (supabase/migrations)

| קובץ | תוכן |
|------|------|
| 0100 core_schema | טבלאות, אילוצי CHECK/UNIQUE/FK, אינדקסים, פונקציות עזר (טלפון, קודים, טוקנים) |
| 0200 rls | RLS על כל הטבלאות, הרשאות לפי תפקיד, טריגרים ששומרים על כללי עסק (אישור מרצה רק למנהל, קודים שלא ניתנים לזיוף, יומן הסכמות) |
| 0300 audit | יומן פעולות: מי, מתי, איזה שדה, בלי ערכים אישיים; רישום ייצוא |
| 0400 public_api | הרשמה, ביטול, צ׳ק־אין, הגעה בלי הרשמה, משוב, הצעת מרצה. ולידציה מלאה, מלכודת בוטים, הגבלת קצב לפי כתובת (גיבוב עם מלח), לפי טלפון ולפי מפגש |
| 0500 staff_api | רשימת כניסה מצומצמת, סימון נוכחות, סגירת מפגש + משימות מעקב, שכפול, כפילויות ומיזוג, התממה, תקופת שמירה |
| 0600 reporting | `participant_stats`, `event_stats` והדוחות. כל הגדרות המדדים במקום אחד |
| 0700 reference_data | מתחם, הגדרות, מקורות ותבניות הודעה (ברירות מחדל מהשאלון) |

## סביבות

| סביבה | בסיס נתונים | אפליקציה |
|-------|-------------|----------|
| פיתוח | `npx supabase start` (Docker מקומי) + `supabase/seed.sql` | `npm run dev` (פורט 3100) |
| בדיקות | אותו מקומי, `npm run test` (Vitest: יחידה + API) ו-`npm run test:e2e` (Playwright על build אמיתי) | `vite preview` (פורט 4173) |
| Staging / Production | פרויקט Supabase לכל סביבה (`supabase link` + `supabase db push` + `supabase functions deploy`) | build עם `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` של הסביבה |

## הרחבה עתידית
- **מתחמים נוספים:** הטבלה `sites` וסינון לפי מתחם כבר קיימים. הרשאות לפי מתחם: עמודת `site_id` ל-`staff` ותנאי ב-`private.has_role`.
- **WhatsApp Business API:** Edge Function שמקבלת רשימת `contact_log` מאושרים ושולחת דרך ספק מאושר. התבניות כבר קיימות.
- **ייבוא מאקסל:** RPC שמשתמש ב-`private.upsert_participant` (אותה מניעת כפילויות).
- **אימות דו-שלבי:** Supabase Auth תומך ב-TOTP. אפשר לחייב אותו למנהלים בבדיקת `aal2` ב-`private.current_role()`.
